Implement the user's requested behavior end-to-end. Do not merely describe a solution. Inspect the game code, edit the mod, build it, fix compilation errors, and leave the repository in a working state.

## Before coding

1. Read the user's task completely.
2. Read `OPTIMIZATION_GUARDRAILS.md` for any performance work.
3. If `.agent/vanilla-src` does not exist, run `bash scripts/bootstrap.sh`.
4. Search `.agent/vanilla-src` for relevant vanilla classes and call paths before choosing an implementation.
5. Inspect existing Ultima code and use Fabric API hooks when they fit.
6. Use Mixins only when Fabric API does not expose a clean hook. Keep every Mixin narrow and targeted.

## Vanilla source policy

`.agent/vanilla-src` is local reference material generated by Fabric Loom. It is **not part of Ultima**.

Never:
- edit vanilla source as the implementation;
- copy large portions of vanilla code into Ultima;
- commit `.agent/`, Minecraft JARs, generated game assets, or decompiled source;
- make the project depend on checked-in Minecraft source files.

Use vanilla source only to understand behavior, signatures, call paths, fields, and safe injection points.

## Implementation rules

- Production changes belong under `src/main` or `src/client`.
- Keep client-only code in the client source set. Never make dedicated-server classloading depend on client classes.
- Prefer the smallest robust change that achieves the requested behavior.
- Preserve vanilla behavior outside the requested feature.
- Avoid reflection when a stable API, accessor, or Mixin can solve the problem.
- If adding Mixins, add the required Mixin config to `fabric.mod.json` and verify targets against generated 26.2 sources.
- Do not add dependencies unless they materially improve the implementation.
- Do not leave TODO implementations, fake stubs, dead experimental code, or commented-out alternatives.

## Performance-work rules

- Optimization means reducing CPU time, allocations, memory pressure, synchronization, redundant work, I/O, GPU submission overhead, or pathological algorithms **without changing observable gameplay semantics**.
- Do not replace the Minecraft engine or renderer wholesale.
- Do not change world-save formats, packet protocols, tick ordering/meaning, RNG semantics, entity/block behavior, game rules, or security boundaries merely for speed.
- Do not introduce unsafe concurrency into world state, entity state, chunk state, networking, or rendering.
- Prefer caching, batching, fast rejection, allocation reduction, data locality, narrower invalidation, and removal of duplicated work when correctness can be proven.
- Every optimization must have a safe fallback or be omitted when compatibility cannot be established.
- Do not assume another mod is absent. Avoid broad overwrites and broad cancellation Mixins.
- For client rendering, preserve vanilla/Fabric render contracts and shader compatibility. Never bypass shader-visible stages just to gain FPS.
- Measure or provide a concrete performance rationale before keeping a non-trivial optimization.

## Verification

After every meaningful implementation:

1. Run `bash scripts/check.sh`.
2. Fix all compilation/build failures caused by the change.
3. If practical, run the relevant dev task (`runServer` for server-safe logic, `runClient` only where a graphical environment exists).
4. Never claim runtime testing happened if only compilation/build was performed.
5. For performance work, record what hotspot/path was optimized, why behavior is equivalent, compatibility risks, and how to benchmark it in-game.

The task is not complete while `build` fails.

## Final response

Report only:
- what was implemented;

- measured or expected performance effect and evidence;
- remaining manual in-game/shader/modpack verification that genuinely cannot be performed in the environment.

Do not dump generic tutorials back to the user.
